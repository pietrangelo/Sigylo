# Sigylo

## MISSION
Share secret data (credentials, keys, codes, files up to 10 MiB) as safely and as simply as possible. The sender seals the secret in the browser, the server keeps only unreadable data, the recipient opens the seal once (or until the chosen expiry) and then the secret is gone.

- **Name:** Sigylo, from *sigillo / sigillum*: the seal that for centuries proved a letter had not been opened before it arrived. Domain: **sigylo.net**, the only production origin.
- **Languages:** Italian, English, French, Spanish and German (`web/src/lib/i18n.ts`). The browser's first language among these wins, otherwise English.
- **Guiding principle:** simplicity first. One field (text or file), two choices (when to destroy it, when it expires), one button. Security must ask nothing of the user.

---

## 0. DEVELOPMENT METHOD

* **TDD:** test first, then code. Every PR says how many tests it adds and what they cover.
* **Rosette:** every bounded context is a pure domain crate with two rings, `core` (immutable, deterministic value objects: no I/O, clock or randomness) inside `application` (use cases and ports). Everything that touches the world lives in separate `<context>-adapters` crates; the **shells** (Wasm, Worker, web, app) only wire.
* **DDD:** ubiquitous language (seal, open, keep, burn, revoke, request), value objects that validate on construction, domain errors as enums.
* **Adversary:** every context has `adversary` test groups that attack the code: bit flips, truncations, swapped keys, hostile parameters, concurrent races, `Debug` that must never print secrets.
* **Architecture guard:** `tools/architecture-guard` fails CI when the rosette breaks. In short: every workspace member declares `[package.metadata.rosette] role` (`domain`, `adapters`, `shell`, `tool`); a domain depends only on `zeroize` and other domains (no build script, target or build dependencies), has `#![forbid(unsafe_code)]`, declares only `core` and `application`, never lets `core` reach `application`, and uses no `std::{fs, net, io, process, env, thread, time, os, path}`, no `include*!`/`env!`/`#[path]` and no console output; an `-adapters` crate never depends on another adapters crate or a shell; crates excluded from the workspace (today only `app/`) are shells or tools; a file that does not parse fails.

## 2. CRYPTOGRAPHY (Sealing context)

Everything happens on the device, in Rust compiled to Wasm. The implementations are pure RustCrypto (constant time, no C), so the same code runs in native tests and in the browser.

| Function | Algorithm | Notes |
|---|---|---|
| KEM (request mode) | X25519 + ML-KEM-768 (FIPS 203) | X-Wing-style: a 32-byte seed expanded with SHAKE256; `ss = SHA3-256(ss_mlkem ‖ ss_x25519 ‖ ct_x25519 ‖ pk_x25519 ‖ label)`. Safe while either one holds. |
| Signature (request mode) | Ed25519 + ML-DSA-65 (FIPS 204) | A 32-byte seed expanded with SHAKE256; both halves sign `label ‖ hybrid public key ‖ message` and both must verify. Deterministic ML-DSA. |
| Encryption | XChaCha20-Poly1305 | Random 192-bit nonce, the whole header as associated data. |
| KDF | HKDF-SHA3-256 | `key = HKDF(salt="sigylo/v1", ikm = base ‖ Argon2id(passphrase), info = "sigylo/v1/aead" ‖ mode)`. |
| Passphrase | Argon2id v1.3 | 64 MiB, 3 passes, 1 lane. On open only 19–256 MiB, 2–10 passes, 1–4 lanes are accepted: a hostile server can neither exhaust RAM nor lower the defence. |
| Padding | Power-of-2 buckets from 256 B | The server cannot tell "hunter2" from a 200-character phrase. At most 64 KiB. |

**Two modes:**
* **Link (default):** a random 256-bit key per secret, only in the URL fragment (`#…`), which browsers never send to servers. 256-bit symmetric keys are already post-quantum (Grover leaves 2^128).
* **Request (hybrid post-quantum):** the recipient generates an X25519 + ML-KEM-768 key pair on their device and publishes only the public key; the sender's link carries the key's SHA3 fingerprint, so a relay that swaps the key is caught before encrypting (`FingerprintMismatch`). No read key ever travels on any channel, and traffic recorded today stays secret against a future quantum computer (HNDL).

**Sender signature (`crates/sealing/src/core/signed.rs`):** every answer to a request is signed with the sender's identity, a 32-byte seed created and kept in their browser's `localStorage` (`web/src/lib/identity.ts`), never sent. The sealed plaintext becomes `public key 1984 B ‖ signature 3373 B ‖ secret` (signed secret limit: 64 KiB − 4 − 5357 B) and the signature covers `"sigylo/v1/signed-answer" ‖ recipient fingerprint ‖ envelope header ‖ secret`: it cannot be resealed for another recipient, nor can a byte of the envelope change. It all sits inside the AEAD, so the relay neither sees who signs nor links two answers from the same sender. Only after the signature verifies does the recipient see the **sender code**: the first 100 bits of the key's SHA3 fingerprint in Crockford base32, `XXXX-XXXX-XXXX-XXXX-XXXX`, to compare by voice or phone; the sender sees the same code on the answer page. An invalid signature gives `NotAuthentic`, like a tampered envelope.

**Chunked files (`crates/sealing/src/core/file.rs`):** a file is a *manifest* sealed in an ordinary v1 envelope (link or request, with or without passphrase), plus its *chunks*. The manifest is `0xFF "SGYF" | version 1 | file key 32 B | size u64 | name length | UTF-8 name`: `0xFF` never appears in UTF-8, so no text is mistaken for a file, and v1 envelopes already issued open as before. Each file has its own random key; 1 MiB chunks are XChaCha20-Poly1305 with key `HKDF(salt="sigylo/v1", file key, info="sigylo/v1/chunk")`, nonce `"SGYC" ‖ index` and associated data `"SGYC" ‖ version ‖ index ‖ chunk count`: reordering, removing, duplicating, truncating chunks or taking them from another file gives `NotAuthentic`. The last chunk is padded to a power of 2 of at least 256 B, all others are full (1 MiB + 16 B): relay and database refuse any other size, and any envelope under 302 B. At most 10 MiB (10 chunks). `FileName` refuses names that could deceive or break a file system (path separators, control, invisible and bidirectional characters, blank glyphs, stacked combining marks, whatever Windows refuses or rewrites); the web client replaces `<>:"|?*` with `_` and strips emoji selectors before sealing, so common names pass. The browser always downloads as `application/octet-stream`, never opened in the page, so a sealed HTML or SVG never runs with Sigylo's origin. An answer carrying a file is signed like a text one: the signature covers the manifest, which carries the file key, hence every chunk.

**Expected sender (optional):** whoever creates the request can type the sender code they expect (the sender finds it at `#/me`). Request and read links carry only the **pin** `HKDF-SHA3-256(salt = "sigylo/v1", ikm = 100 bits of the code, info = "sigylo/v1/expected-sender" ‖ recipient fingerprint)`, different for every request: the link does not reveal the code and two requests to the same sender are unlinkable. On open, an unsigned answer or one signed by someone else gives `UnexpectedSender` and the plaintext is zeroed without being shown; the answer page warns a different sender at once, so they do not consume the request's only answer. The code is accepted as a person dictates it: any case, with or without dashes, I/L for 1 and O for 0.

**Envelope (`crates/sealing/src/core/envelope.rs`):** `"SGY" | version 1 | mode | flags | [salt + Argon2id costs] | [encapsulation 1120 B] | nonce 24 B | ciphertext + tag`. Flags: bit 0 passphrase, bit 1 signed (request mode only); the flags sit in the authenticated header, so they cannot be removed or added. An envelope without bit 1 is byte-for-byte identical to first-version ones, and old links still open. The parser is strict and canonical. The `format_pin` tests pin the bytes: if they change, bump the version, do not update the constants.

**Indistinguishable errors:** wrong key, wrong passphrase, wrong recipient, invalid signature and tampered envelope all give `NotAuthentic`.

**Memory:** keys, seeds, passphrases and plaintext are `Zeroize` types with redacted `Debug`. The Wasm shell hands them to JavaScript by copying straight into a `Uint8Array` (never as a `Vec<u8>` or a field of an exported struct, which wasm-bindgen moves or frees without zeroing) and after every call overwrites 512 KiB of stack (ML-DSA-65 key expansion reaches about 290 KiB, with secret vectors on the stack), where moves leave copies `Zeroize` cannot reach. `web/tests/engine-memory.test.ts` scans Wasm memory after every operation and fails if it finds a secret or a single non-zeroed byte in the dead part of the stack. Known browser limit: whatever passes through a JS string or `Uint8Array` may linger in garbage-collector copies.

## 3. CUSTODY (Custody context) AND THE BLIND RELAY

* **The relay is blind:** it receives already-sealed envelopes (opaque bytes) and, for revocation, a token of which it keeps only the SHA-256. It does not log ids, payloads or addresses.
* **Ids are chosen by the relay, never the client:** 128 random bits (port `IdSource`, adapter `RandomIds`), returned in the receipt `{id, expires_at}`. A request carrying its own `id` is refused. Otherwise whoever first reads a burn-after-reading secret could put back a copy, or a forgery sealed with the link key, under the same id, and the recipient would open it unaware: the seal would be broken.
* **Rules:** lifetime from 5 minutes to 7 days; `BurnAfterReading` returns the envelope **at most once** even under concurrent reads; `UntilExpiry` is readable until expiry; missing, expired, already read and revoked are indistinguishable (`404 NotFound`); a live id is never overwritten; a request gets at most one answer.
* **Private request inbox:** for each request the relay picks two ids, the public one in the request link and the `inbox` one, which is only in the recipient's private link; the answer is stored in the inbox. So whoever reads the request link on its way to the sender can neither burn the answer before the recipient nor download it. Requests created before the inbox (empty `inbox_id`) get the answer under their own id, as then. The sender gets the inbox id in the receipt `{id, expires_at}` and uploads a file's chunks there (`custody.answer_into_inbox`): the request link alone cannot add or spoil a chunk.
* **Request mode and sender:** with an expected sender, anyone else's answer is refused unread (but it consumes the request: the recipient creates another). Without an expected sender anyone holding the request link can still answer first, but is caught: the recipient sees a sender code different from the one the legitimate sender reads to them, and the legitimate sender sees "request already used". The code needs comparing out of band once; it then stays the same until the sender clears the site's data. Known limit: whoever controls the sender's browser (extension, XSS) can read the seed from `localStorage` and sign in their place.
* **Files:** the deposit (or answer) carries the sealed manifest and `chunks`; chunks are uploaded afterwards, one per request, each once, and only while nobody has opened the deposit. An incomplete file does not open (`404`) and expires within 10 minutes: the last chunk restores the chosen lifetime, so nobody fills space with uploads never finished. Opening a `BurnAfterReading` file does not delete it but *claims* it: the relay picks a random token, keeps only its SHA-256 and returns it only to whoever opened; from then on the deposit does not reopen, each chunk goes only to whoever presents the token, at most once, and is deleted as it leaves; the deposit goes with the last chunk, and an abandoned download expires within an hour. An `UntilExpiry` file stays downloadable by anyone with the link until expiry. If an upload breaks off (network, `429`, `507`) the client keeps in memory id, sealed chunks and each index's state (`web/src/lib/files.ts`) and offers a retry that sends only the missing chunks: that is what saves an answer, which has already consumed the request. A `404` on an index whose earlier send may have arrived (network drop, `5xx`) means "already in"; on one that surely did not arrive it means the deposit is gone, and the sender is asked for a new request.
* **Chunks on R2, never in the database:** the relay stores each chunk as an object in the R2 bucket `sigylo-chunks` (EU jurisdiction) under a random 128-bit name it picks (`IdSource::fresh_object`), which says nothing about the deposit. Before writing to R2, `custody.reserve_chunk` refuses a chunk the deposit does not take (nothing is written) and records the name in `custody.garbage` for 15 minutes; afterwards `custody.record_chunk` turns the fresh reservation into a chunk, and a refused object is deleted at once. An index already taken is a refusal like the others (`404`). PostgreSQL keeps only name and size. Every chunk that leaves (burned, revoked, expired, cascades included) leaves name and size in `custody.garbage`, collected no sooner than 5 minutes (`not_before`); the cron deletes those objects from R2 and only then forgets them, so an R2 error loses track of nothing. A chunk to burn is found (`custody.find_chunk`), read from R2 and only then burned (`custody.burn_chunk`), so an R2 error does not lose it; it disappears from R2 as it leaves. A revoked one disappears at once (`custody.revoke_with_objects`), an expired one within about 20 minutes; a bucket lifecycle rule (8 days) is the backstop.
* **API (`worker/src/api.rs`):** `POST /api/secrets`, `POST /api/secrets/{id}/open`, `POST /api/secrets/{id}/revoke`, `POST /api/secrets/{id}/chunks/{n}`, `POST /api/secrets/{id}/chunks/{n}/open`, `POST /api/requests`, `GET /api/requests/{id}`, `POST /api/requests/{id}/answer`. Opening is always a POST: link previews and prefetches (GET) cannot burn a secret. Binary fields in unpadded base64url, except chunks, which travel as raw binary bodies (no 1 MiB base64 in the Worker's 10 ms of CPU). The body is validated (including the declared `Content-Length`, required on every route with a body: without it, `411` before reading) before opening a database connection.
* **Rate limits:** Cloudflare bindings `WRITE_LIMITER` (POST, 30/min) and `READ_LIMITER` (GET, 60/min) on every API call (GETs too: each costs a query) per address, IPv6 per /64 (`limiter_key`); IPv6 POSTs also count per /48 (`NETWORK_WRITE_LIMITER`, 300/min, `network_key`), because a free tunnel gives anyone 65,536 /64s; kept in Cloudflare's memory, never stored by us.
* **Only from our pages:** a call with an `Origin` header other than the relay's origin gets `403` (`check_origin`), so another site's page cannot use its visitors' browsers to fill the custody around the per-address limit. Without `Origin` (the app shell) it passes.

## 3-bis. OPTIONAL ACCOUNTS (Access context, OPAQUE login)

* **What they are for:** a signed-in user finds in "Your seals" the secrets sealed while signed in and can destroy them from any device. Without an account everything works as before. No e-mail: only username and password.
* **OPAQUE (RFC 9807, `opaque-ke` 4.0):** the password never leaves the device, not even as a hash, and the server keeps only a record from which it cannot be tested offline. Suite: Ristretto255 OPRF, 3DH key exchange (Ristretto255, SHA-512), Argon2id v1.3 KSF 64 MiB, 3 passes, 1 lane (`HARDENING_*` in `suite.rs`). Passwords 8–1024 bytes; the name is lowercased (NFC in the client), 3–64 characters.
* **Relay keys:** all derived from a single Worker secret `OPAQUE_SERVER_SEED` (32 bytes base64url) with HKDF-SHA512: a deterministic `ServerSetup` (pinned by `tests/opaque_pin.rs`: if the seed or the derivation changes, every existing account stops working) and the HMAC key of `AccountId = HMAC-SHA256(k, "sigylo/v1/account\0" ‖ name)`. The database never sees the name. The deploy workflow creates the secret if missing; it **must never be rotated** without an account migration.
* **Indistinguishability:** unknown name and wrong password give the same `401` (`opaque-ke` fake record); the one known limit is that registration reveals whether a name is taken (`409`).
* **Sessions:** 32-byte tokens; the server keeps only their HMAC-SHA256 under a key derived from `OPAQUE_SERVER_SEED` (`OpaqueKeys::session_digest`), so a stolen database credential can write a session row but never hold a matching token; 12-hour lifetime (`SESSION_SECONDS`, also enforced by `access.open_session`); the client keeps it only in the tab's memory (a reload signs out). At most 16 sessions per account (`MAX_SESSIONS`, enforced by `access.open_session`): one more closes the one expiring first. "Sign out everywhere" (`access.close_sessions`) closes every session of the account, leaving account and keyring untouched. The state between the two login steps lives in the database for 5 minutes and is single-use (`LOGIN_WINDOW_SECONDS`).
* **Keyring:** `HKDF-SHA512(export_key, "sigylo/v1/keyring")` gives a 256-bit key that seals (a link-mode envelope, `Sealer::seal_with_link_key`) a JSON of seal ids and revocation tokens, never read links; at most 72 KiB and 300 seals. Writes use an optimistic version: on `409 Conflict` the client rereads and reapplies the change. That version is not authenticated, so the sealed JSON also carries its own generation (`gen`, +1 per write; a keyring without it counts as 0) and each device remembers in `localStorage` the highest it has seen, under `sigylo.keyring.v1.` + 128 bits of SHA-256(`"sigylo/v1/keyring-watermark"` ‖ keyring key), never the name (`web/src/lib/keyring.ts`): an older copy (even "no keyring") gives `KeyringRolledBack`, a warning, and is never overwritten. Known limit: a device that has never seen the account has nothing to compare with, and storage that refuses turns the check off.
* **Throttle:** 10 attempts a minute per account and per budget, counted once for the whole world in the database (`access.admit`, `PostgresThrottle`: a one-minute window per key, deleted by the cron). Three separate budgets (`Budget`, keys from `throttle_bucket`): the shared login, registering a free name, and each **device pass**. A taken name answers `409` before spending budget. After each login the relay hands out a pass (`HmacPasses`: 90-day expiry ‖ nonce ‖ HMAC over account and SHA-256 of the record, key from `OPAQUE_SERVER_SEED`, nothing stored); the client keeps it in `localStorage` (`sigylo.pass.v1`, under a hash of the name) and shows it at the next login, which spends a budget of its own: whoever guesses passwords on the name exhausts only the shared budget and does not lock out the owner's devices. A pass opens nothing, and a new record (the name passed to someone else) voids it. The `LOGIN_LIMITER` binding stays in front as a cheap first filter, but counts per Cloudflare location and is not enough alone. If either does not answer, the call is refused (fail closed).
* **No oracle in registration:** `register/start` for a taken name answers `409` at once without evaluating the OPRF: with the evaluation under the account's key, anyone holding the victim's KE2 could test passwords offline.
* **Sealed login state:** the `ServerLogin` state parked in the database is encrypted with XChaCha20-Poly1305 (key from `OPAQUE_SERVER_SEED`, AAD = account ‖ SHA-256 of the record): whoever can write `access.logins` can neither plant their own state nor move it to another account, and a login started before a name changed hands does not enter the new account.
* **API:** `POST /api/account/register/start|finish`, `POST /api/account/login/start|finish` (`login/start` accepts `pass`, `login/finish` returns it), `POST /api/account/logout`, `POST /api/account/logout/everywhere`, `GET|POST /api/account/keyring`, `POST /api/account/close`, with `Authorization: Bearer <token>` where a session is needed; `GET /api/account/canary` (public, see §6).
* **Known limits:** OPRF and 3DH are not post-quantum (transcripts travel inside TLS anyway; `opaque-ke` 4.1 will have a hybrid KEM); no password change or recovery: whoever forgets it loses the keyring, not the secrets.

## 3-ter. THE VAULT (Vault context, Durable Object + R2)

* **Where custody lives:** a single Durable Object `SigyloVault`, created by name in the `eu` jurisdiction (`vault_adapters::DurableLink`), with its SQLite storage used only through the synchronous key-value API: no SQL, the format is ours (`crates/vault/src/core/records.rs`, `keys.rs`). Envelopes and chunks live in R2 (bucket `sigylo-chunks`) under random 128-bit names, never in the Durable Object, because its storage keeps 30 days of history (point-in-time recovery): a burned secret must not survive there. The Durable Object holds only ids, expiries, rules, revocation and claim digests, object names and sizes.
* **One step, one transaction:** every `Ledger` operation is a synchronous step inside `transactionSync` (`KeyValue::atomically`): all or nothing, and the Durable Object runs one step at a time, so burn-after-reading delivers at most once. `LedgerVault` interleaves the steps with R2: find, read from R2, then burn; reserve the envelope's name (in `garbage`, already counted in the cap), write to R2, then record, and delete the object if the ledger refuses. An R2 error or a Durable Object restart loses nothing: an envelope never recorded is collected by the cron.
* **Same rules as SQL custody:** lifetimes, incomplete files for 10 minutes, one-hour claim, chunk reservation (15 minutes) and `garbage` with 5 minutes' grace, a cap of 50 GiB of objects and 1,000,000 records; in addition, beyond 1,000,000 rows written in a (UTC) day nothing new is kept, while open, burn, revoke and purge go on, and beyond 2,000,000 purge and collection also wait for the next day (whatever expired is already invisible). The vault runs on the Workers Paid plan: past the 50 million included rows a month it costs $1 per million and nothing blocks, so the thresholds only cap the bill (about $1 a day for sealing). On the free plan (100,000 rows a day, then every write fails until UTC midnight) a flood would stop open, burn and revoke for everyone: the thresholds would have to go back under half that limit. Records are validated strictly (`decode`), and a damaged record gives `VaultUnavailable`, never a secret.
* **The wire:** the Worker talks to the vault with a single request per call (`RemoteVault` → binary `Call`/`Reply`, `serve` in the Durable Object). The claim token never crosses the wire, only its digest.
* **Migration (`Draining`):** with `LEGACY_VAULT = "drain"` new deposits always go to the vault, and whatever the vault does not know is still looked up in PostgreSQL (open, revoke, answer a request, chunks, purge), until the last thing kept there expires (7 days at most). If PostgreSQL does not answer, the vault keeps purging and collecting alone; a lookup the vault misses answers `503`, because the secret might still be there. Then the variable is removed and, in a later PR, the `custody` code and schema.
* **Local only:** `VAULT_PLACEMENT = "local"` (passed by `scripts/e2e.sh` to `wrangler dev`, whose runtime has no jurisdictions) and `DB_TLS = "disable"` must never be in `wrangler.toml`: the deploy fails if they are.

## 4. PERSISTENCE (Supabase PostgreSQL via Hyperdrive: accounts, and custody while it drains)

* The `custody` schema rules below apply to the draining custody (§3-ter); new custody lives in the vault. The `access` schema stays here until accounts move to the vault too.
* `custody` schema with five tables (`deposits`, `requests`, `chunks`, `garbage`, `usage`) and **21 columns in all** (checked by tests): no creation times, no IPs, no accounts. `bytea` columns, length constraints in the database.
* Every operation is a `SECURITY DEFINER` function with an empty `search_path`; burn-after-reading is a single atomic `DELETE … RETURNING`; the clock that decides expiry is only the database's `now()`.
* **No Hyperdrive cache:** Hyperdrive caches for a minute the `SELECT`s it believes read-only and does not see that `custody.open` deletes; a cached answer would return a secret already burned, revoked or expired. The Hyperdrive config is created with `--caching-disabled` and, on top, every vault statement also selects `now()`, which Hyperdrive never caches (test in `postgres_vault.rs`).
* The Worker connects as `sigylo_relay`, which can **only execute the functions**: no table privileges, so a stolen relay credential cannot list or download secrets. No other role, neither `PUBLIC` nor Supabase's `anon`/`authenticated`/`service_role`, has privileges in the `custody` schema (checked on the ACLs by tests, with the Supabase roles recreated). RLS enabled and forced.
* Off by choice: Supabase Auth, supabase-js in the browser, Vault/pgsodium (encryption never happens in the database), PostgREST on the `custody` schema.
* `access` schema with five tables (`accounts`, `logins`, `sessions`, `attempts`, `usage`) and **17 columns in all**, same rules: `SECURITY DEFINER` functions, EXECUTE only for `sigylo_relay`, forced RLS, no plaintext username, no creation time (`attempts` keeps only the start of the current one-minute window).
* **Account cap:** accounts do not expire, so they have their own cap, with the same `53100` → `507 StorageFull`: 64 MiB for accounts and keyrings (`access.capacity_bytes()`) and a separate 16 MiB for logins in progress, sessions and counters (`access.transient_capacity_bytes()`), so a login flood does not block registrations and a full store does not block sign-ins. Each row weighs a fixed cost (`access.row_cost`) plus its keyring, in a counter kept by triggers (`access.usage`), without scans. At the cap you can still sign in, read, and rewrite a keyring no larger than before.
* A cron every 15 minutes (`purge_expired`) physically deletes what has expired, in the vault and in both schemas; chunks follow their deposit (`on delete cascade`). The same Worker cron then collects the due `garbage` and deletes the objects from R2, in batches of 1000, while it finds some and for at most 5 batches or 10 seconds.
* **Custody cap:** the free database stops at 500 MB and then goes read-only (nothing opens any more). `custody.ensure_room` (for deposits in a trigger on `custody.deposits`, so it holds whatever version of `custody.deposit` runs) refuses any new deposit, request or answer beyond `custody.capacity_bytes()` (300 MB of kept bytes plus a fixed cost per row, 192 B per deposit or chunk and 128 per request or garbage, so many small rows do not slip through; kept in the single-row table `custody.usage`, updated by triggers, and read by `custody.used_bytes()` without scanning tables or looking at files on disk, which do not shrink) with SQLSTATE `53100`, which the relay returns as `507 StorageFull`. Before refusing it deletes whatever has expired; open, revoke and purge always work. Every new table that keeps bytes must be counted in `used_bytes`.
* **Chunk cap:** all chunks together, plus objects still in `garbage`, stay under 5 GiB (`custody.reserve_chunk` reads `custody.usage` under a lock, so concurrent uploads do not overshoot, and fails with `53100`; the relay answers `507 StorageFull`), half of R2's free 10 GB. The database never holds chunk bytes (checked by tests). With the 30 POST a minute per address limit, a 10 MiB file costs 11 requests to upload and 11 to download.
* Migrations are additive: functions from the first one keep their signature (the old `custody.open(bytea)` ignores files), so the production relay keeps working while a new migration is applied, before the deploy.

## 5. WEB CLIENT AND CODE INTEGRITY

* Svelte 5 (runes) + strict TypeScript; no runtime dependency beyond the compiled code.
* Served by the Worker itself (Workers Static Assets): a single origin, hence `connect-src 'self'` and no CORS.
* **CSP** (`web/public/_headers`): `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, plus `Referrer-Policy: no-referrer`, COOP, CORP, HSTS, `nosniff`, `X-Frame-Options: DENY`. No `unsafe-inline`: no inline scripts or styles.
* **SRI** (`web/vite-plugin-integrity.ts`): sha384 `integrity` on scripts and stylesheets, and the `.wasm` is fetched with `fetch(url, { integrity })`.
* After opening, the key is removed from the address bar (`history.replaceState`).
* **UI:** everything follows the golden ratio φ (`web/src/lib/golden.ts`): Fibonacci spacing around 8 px, type in φ steps from 16 px, 610 px column, and a "sealing wax" OKLCH palette whose hues turn by the golden angle, light and dark themes. `app.css` fixes the values in hex; `web/tests/golden.test.ts` fails if they drift from the computation, if a colour or length outside the tokens appears, or if a pair loses WCAG contrast (text AAA 7:1, secondary text, errors and states AA 4.5:1, graphics 3:1).
* **Terms and privacy** (`web/src/lib/legal.ts`, pages `#/terms` and `#/privacy`, footer links in a new tab so an open secret link does not lose its fragment): text only, never `{@html}` (checked by tests). The Apache License 2.0 covers the code; the terms cover only the service on sigylo.net. Operator and contact live in `operator` and in the `NOTICE` file: a test fails CI, and so the deploy, while they contain `DA COMPILARE`. When a text changes, update `LEGAL_UPDATED`; when providers, kept data or maximum lifetime change, update the privacy notice. `web/public/.well-known/security.txt` (RFC 9116) and `SECURITY.md` say whom to report a vulnerability to: a test fails CI once the `Expires` date has passed.
* **Known limit:** whoever controls the hosting can serve a different `index.html`. SRI protects subresources, not the page itself. Whoever wants to avoid that has the app (below); signed and verifiable builds are deferred (§7).

**Installable app (`app/`, Tauri 2):**
* `vite build --mode app` (`npm run build:app`, into `web/dist-app`) produces the same page with the Wasm engine, embedded in the app: while the app runs no code comes from a server, and there is no updater.
* The page has no network: the app CSP (`vite-plugin-app.ts`, identical to the one in `tauri.conf.json`, checked by tests) has `connect-src 'self' ipc: http://ipc.localhost`. Relay calls go through the Rust command `relay` (`app/src/relay.rs`), which accepts only the API routes with their method (the account session token only on the routes that need it, validated and sent as `Authorization: Bearer`) and goes only to `https://sigylo.net/api`: no redirects, no cookies, HTTPS only, body ≤ 100 KiB, response ≤ 128 KiB. File chunks cross the IPC in canonical base64url (at most 1 MiB + 16 bytes, single-digit index) and travel to the relay as raw bytes. So the Worker stays without CORS.
* An opened file is saved to the Downloads folder: the webview follows only a `blob:` created by the page itself (always `application/octet-stream` with a download name), never shown. The page has only two permissions (`capabilities/main.json`: `allow-relay`, `allow-open-legal`), no Tauri or plugin permission, no `withGlobalTauri`, `freezePrototype` on; the webview does not navigate outside the bundle (`navigation.rs`).
* Links created in the app are `https://sigylo.net/#/…` (they open in any browser); a received link is pasted into the app's box (`linkFragment` accepts only `https://sigylo.net/` with a secret, revoke, request or inbox fragment). Terms and privacy open in the system browser.
* Release: `.github/workflows/app-release.yml` (`app-v*` tag or by hand) creates unsigned Linux, macOS and Windows installers in a draft release. Signing and stores need the owner's accounts. Mobile: crate ready (`mobile_entry_point`), native projects to be generated with `cargo tauri android init` / `ios init`.

## 6. DEPLOY

1. Supabase, in a project dedicated to Sigylo: apply `supabase/migrations/*.sql` in order (a new migration is applied **before** merging the PR that uses it: migrations stay compatible with the relay already published), then `alter role sigylo_relay login password '<strong password>';`.
2. Cloudflare: `npx wrangler hyperdrive create sigylo-db --caching-disabled --connection-string="postgres://sigylo_relay:<password>@<host>:5432/postgres"` and put the id in `worker/wrangler.toml`. `--caching-disabled` is mandatory (see §4); on an existing config: `npx wrangler hyperdrive update <id> --caching-disabled`.
   R2: `npx wrangler r2 bucket create sigylo-chunks --jurisdiction eu` and, as a backstop, `npx wrangler r2 bucket lifecycle add sigylo-chunks backstop --expire-days 8 --jurisdiction eu`, which the deploy workflow adds by itself if missing (the deploy token must be able to edit R2).
   Vault: the `SigyloVault` Durable Object is born with the deploy (`[[migrations]]` in `wrangler.toml`, SQLite class); the R2 bucket is the same as the chunks'.
3. Publication on `https://sigylo.net` (Worker custom domain, `workers.dev` off). Normally done by `.github/workflows/deploy.yml`: it runs only on `main`, only after CI passed on that same commit, never from a pull request, and only if the commit is still the tip of `main`. Its secrets (`CLOUDFLARE_API_TOKEN`, "Edit Cloudflare Workers" template limited to this account and the sigylo.net zone, and `CLOUDFLARE_ACCOUNT_ID`) belong to the GitHub environment `production`, open to `main` only, never to the repository, so a workflow pushed on another branch cannot read them. Every GitHub action is pinned to a commit (`uses: owner/action@<sha> # tag`, checked by CI): a moved tag of a third-party action would run next to the token and the page to publish. By hand: `(cd web && npm ci && npm run build)` then `(cd worker && npx wrangler deploy)`.
4. Worker secret `OPAQUE_SERVER_SEED` (§3-bis): after the deploy the workflow creates it with 32 random bytes if it does not exist and never touches it again. By hand: `openssl rand 32 | basenc --base64url | tr -d '=\n' | npx wrangler secret put OPAQUE_SERVER_SEED`. Without the secret accounts answer `503` and the rest works. **Canary:** `GET /api/account/canary` returns a public fingerprint of the secret (`OpaqueKeys::canary`, HKDF "canary"); the `OPAQUE_CANARY` variable in `worker/wrangler.toml` records the one the accounts were created with. When set, accounts answer `503` under any other secret, the workflow stops instead of creating a new secret when it is missing, and fails if the published canary differs; when empty, the workflow prints the value to paste.
5. In the sigylo.net zone turn off every Cloudflare feature that rewrites HTML (Rocket Loader, Email Obfuscation, automatic Web Analytics): they would break CSP and SRI. After every deploy the workflow checks that the served page is byte-for-byte identical to `web/dist/index.html` and carries the `_headers` CSP, and fails if the zone rewrites it.

## 7. DEFERRED (not in the MVP)

* **Non-exportable signing keys** in the verifiable client (Tauri, Secure Enclave / TPM); refusing an unexpected sender's answer already at the relay would need the relay to see who signs, so it stays client-side.
* **Accounts, second phase:** password change and recovery, OPAQUE with a hybrid post-quantum KEM (when `opaque-ke` 4.1 is stable), sessions that survive a reload. The link stays the capability: the account keeps only revocation tokens (§3-bis).
* **Verifiable client:** signed, reproducible app builds, keys in Secure Enclave / TPM, or a signed browser extension. Opening `https://sigylo.net` links straight in the app (universal/app links) needs the developer accounts' identifiers.
* **Files over 10 MiB:** R2 storage is already there; it would need more chunks per file and, beyond some size, multipart upload.
* **Blind index:** not needed until server-side search exists.
