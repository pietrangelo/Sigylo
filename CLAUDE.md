# Sigylo

## MISSION
Share secret data (credentials, keys, codes, files up to 10 MiB) as safely and as simply as possible. The sender seals the secret in the browser, the server keeps only unreadable data, the recipient opens the seal once (or until the chosen expiry) and then the secret is gone.

- **Name:** Sigylo, from *sigillo / sigillum*: the seal that for centuries proved a letter had not been opened before it arrived. Domain: **sigylo.net**, the only production origin.
- **Languages:** Italian, English, French, Spanish and German (`web/src/lib/i18n.ts`). The browser's first language among these wins, otherwise English.
- **Guiding principle:** simplicity first. One field (text or file), two choices (when to destroy it, when it expires), one button. Security must ask nothing of the user.

---

## 0. DEVELOPMENT METHOD

* **TDD:** test first, then code. Every PR says how many tests it adds and what they cover.
* **Rosette:** every bounded context is a pure domain crate with two rings, `core` (immutable, deterministic value objects: no I/O, clock or randomness) inside `application` (use cases and ports). Everything that touches the world lives in separate `<context>-adapters` crates; the **shells** (Wasm, Worker, web, app) only wire.
* **DDD:** ubiquitous language (seal, open, keep, burn, revoke, request), value objects that validate on construction, domain errors as enums.
* **Adversary:** every context has `adversary` test groups that attack the code: bit flips, truncations, swapped keys, hostile parameters, concurrent races, `Debug` that must never print secrets.
* **Architecture guard:** `tools/architecture-guard` fails CI when the rosette breaks. In short: every workspace member declares `[package.metadata.rosette] role` (`domain`, `adapters`, `shell`, `tool`); a domain depends only on `zeroize` and other domains (no build script, target or build dependencies), has `#![forbid(unsafe_code)]`, declares only `core` and `application`, never lets `core` reach `application`, and uses no `std::{fs, net, io, process, env, thread, time, os, path}`, no `include*!`/`env!`/`#[path]` and no console output (macros called inside other macros included); `core` imports nothing from the crate root, neither by `crate::` nor by `super` paths that climb to it, nor by a glob; an `-adapters` crate never depends on another adapters crate or a shell; crates excluded from the workspace (today only `app/`) are shells or tools; a file that does not parse fails.

## 2. CRYPTOGRAPHY (Sealing context)

Everything happens on the device, in Rust compiled to Wasm. The implementations are pure RustCrypto (constant time, no C), so the same code runs in native tests and in the browser.

| Function | Algorithm | Notes |
|---|---|---|
| KEM (request mode) | X25519 + ML-KEM-768 (FIPS 203) | X-Wing-style: a 32-byte seed expanded with SHAKE256; `ss = SHA3-256(ss_mlkem ‖ ss_x25519 ‖ ct_x25519 ‖ pk_x25519 ‖ label)`. Safe while either one holds. |
| Signature (request mode) | Ed25519 + ML-DSA-65 (FIPS 204) | A 32-byte seed expanded with SHAKE256; both halves sign `label ‖ hybrid public key ‖ message` and both must verify. Deterministic ML-DSA. |
| Encryption | XChaCha20-Poly1305 | Random 192-bit nonce, the whole header as associated data. |
| KDF | HKDF-SHA3-256 | `key = HKDF(salt="sigylo/v1", ikm = base ‖ Argon2id(passphrase), info = "sigylo/v1/aead" ‖ mode)`. |
| Passphrase | Argon2id v1.3 | 64 MiB, 3 passes, 1 lane. On open only 19–256 MiB, 2–10 passes, 1–4 lanes are accepted: a hostile server can neither exhaust RAM nor lower the defence. |
| Padding | Power-of-2 buckets from 256 B | The server cannot tell "hunter2" from a 200-character phrase. At most 64 KiB. |

**Two modes:**
* **Link (default):** a random 256-bit key per secret, only in the URL fragment (`#…`), which browsers never send to servers. 256-bit symmetric keys are already post-quantum (Grover leaves 2^128).
* **Request (hybrid post-quantum):** the recipient generates an X25519 + ML-KEM-768 key pair on their device and publishes only the public key; the sender's link carries the key's SHA3 fingerprint, so a relay that swaps the key is caught before encrypting (`FingerprintMismatch`). No read key ever travels on any channel, and traffic recorded today stays secret against a future quantum computer (HNDL).

**Sender signature (`crates/sealing/src/core/signed.rs`):** every answer to a request is signed with the sender's identity, a 32-byte seed created and kept in their browser's `localStorage` (`web/src/lib/identity.ts`), never sent. The sealed plaintext becomes `public key 1984 B ‖ signature 3373 B ‖ secret` (signed secret limit: 64 KiB − 4 − 5357 B) and the signature covers `"sigylo/v1/signed-answer" ‖ recipient fingerprint ‖ envelope header ‖ secret`: it cannot be resealed for another recipient, nor can a byte of the envelope change. It all sits inside the AEAD, so the relay neither sees who signs nor links two answers from the same sender. Only after the signature verifies does the recipient see the **sender code**: the first 100 bits of the key's SHA3 fingerprint in Crockford base32, `XXXX-XXXX-XXXX-XXXX-XXXX`, to compare by voice or phone; the sender sees the same code on the answer page. An invalid signature gives `NotAuthentic`, like a tampered envelope.

**Chunked files (`crates/sealing/src/core/file.rs`):** a file is a *manifest* sealed in an ordinary v1 envelope (link or request, with or without passphrase), plus its *chunks*. The manifest is `0xFF "SGYF" | version 1 | file key 32 B | size u64 | name length | UTF-8 name`: `0xFF` never appears in UTF-8, so no text is mistaken for a file, and v1 envelopes already issued open as before. Each file has its own random key; 1 MiB chunks are XChaCha20-Poly1305 with key `HKDF(salt="sigylo/v1", file key, info="sigylo/v1/chunk")`, nonce `"SGYC" ‖ index` and associated data `"SGYC" ‖ version ‖ index ‖ chunk count`: reordering, removing, duplicating, truncating chunks or taking them from another file gives `NotAuthentic`. The last chunk is padded to a power of 2 of at least 256 B, all others are full (1 MiB + 16 B): relay and vault refuse any other size, and any envelope under 302 B. At most 10 MiB (10 chunks). `FileName` refuses names that could deceive or break a file system (path separators, control, invisible and bidirectional characters, blank glyphs, stacked combining marks, whatever Windows refuses or rewrites); the web client replaces `<>:"|?*` with `_`, strips emoji selectors and turns no-break spaces (macOS puts U+202F in screenshot names) into plain ones before sealing, so common names pass. Marks are counted per character by Unicode category (`core/marks.rs`, Mn and Me): at most 2 from the generic combining blocks and 4 of any script. A manifest whose name these rules refuse (sealed under looser ones, by an older client or an app without updates) still opens, as `file` plus its extension when that passes; an empty name is malformed. The browser always downloads as `application/octet-stream`, never opened in the page, so a sealed HTML or SVG never runs with Sigylo's origin. An answer carrying a file is signed like a text one: the signature covers the manifest, which carries the file key, hence every chunk.

**Expected sender (optional):** whoever creates the request can type the sender code they expect (the sender finds it at `#/me`). Request and read links carry only the **pin** `HKDF-SHA3-256(salt = "sigylo/v1", ikm = 100 bits of the code, info = "sigylo/v1/expected-sender" ‖ recipient fingerprint)`, different for every request: the link does not reveal the code and two requests to the same sender are unlinkable. On open, an unsigned answer or one signed by someone else gives `UnexpectedSender` and the plaintext is zeroed without being shown; the answer page warns a different sender at once, so they do not consume the request's only answer. The code is accepted as a person dictates it: any case, with or without dashes, I/L for 1 and O for 0.

**Envelope (`crates/sealing/src/core/envelope.rs`):** `"SGY" | version 1 | mode | flags | [salt + Argon2id costs] | [encapsulation 1120 B] | nonce 24 B | ciphertext + tag`. Flags: bit 0 passphrase, bit 1 signed (request mode only); the flags sit in the authenticated header, so they cannot be removed or added. An envelope without bit 1 is byte-for-byte identical to first-version ones, and old links still open. The parser is strict and canonical. The `format_pin` tests pin the bytes: if they change, bump the version, do not update the constants.

**Indistinguishable errors:** wrong key, wrong passphrase, wrong recipient, invalid signature and tampered envelope all give `NotAuthentic`.

**Memory:** keys, seeds, passphrases and plaintext are `Zeroize` types with redacted `Debug`. The Wasm shell hands them to JavaScript by copying straight into a `Uint8Array` (never as a `Vec<u8>` or a field of an exported struct, which wasm-bindgen moves or frees without zeroing) and guards every secret argument with `Zeroizing` before checking any of them, keeps a pending OPAQUE state on the heap and overwrites it there when it is taken, and after every call overwrites 512 KiB of stack (ML-DSA-65 key expansion reaches about 290 KiB, with secret vectors on the stack), where moves leave copies `Zeroize` cannot reach. `web/tests/engine-memory.test.ts` scans Wasm memory after every operation and fails if it finds a secret or a single non-zeroed byte in the dead part of the stack. Known browser limit: whatever passes through a JS string or `Uint8Array` may linger in garbage-collector copies.

## 3. CUSTODY (Custody context) AND THE BLIND RELAY

* **The relay is blind:** it receives already-sealed envelopes (opaque bytes) and, for revocation, a token of which it keeps only the SHA-256. It does not log ids, payloads or addresses.
* **Ids are chosen by the relay, never the client:** 128 random bits (port `IdSource`, adapter `RandomIds`), returned in the receipt `{id, expires_at}`. A request carrying its own `id` is refused. Otherwise whoever first reads a burn-after-reading secret could put back a copy, or a forgery sealed with the link key, under the same id, and the recipient would open it unaware: the seal would be broken.
* **Rules:** lifetime from 5 minutes to 7 days; `BurnAfterReading` returns the envelope **at most once** even under concurrent reads; `UntilExpiry` is readable until expiry; missing, expired, already read and revoked are indistinguishable (`404 NotFound`); a live id is never overwritten; a request gets at most one answer.
* **Private request inbox:** for each request the relay picks two ids, the public one in the request link and the `inbox` one, which is only in the recipient's private link; the answer is stored in the inbox. So whoever reads the request link on its way to the sender can neither burn the answer before the recipient nor download it. Requests created before the inbox (empty `inbox_id`) get the answer under their own id, as then. The sender gets the inbox id in the receipt `{id, expires_at}` and uploads a file's chunks there (`Vault::answer_request` stores the answer under the inbox id): the request link alone cannot add or spoil a chunk.
* **Request mode and sender:** with an expected sender, anyone else's answer is refused unread (but it consumes the request: the recipient creates another). Without an expected sender anyone holding the request link can still answer first, but is caught: the recipient sees a sender code different from the one the legitimate sender reads to them, and the legitimate sender sees "request already used" (unless their own send broke off before its receipt: then the page says the answer may have arrived, `answerMessage` in `web/src/lib/messages.ts`; making the answer POST idempotent needs an answer nonce, deferred). The code needs comparing out of band once; it then stays the same until the sender clears the site's data. Known limit: whoever controls the sender's browser (extension, XSS) can read the seed from `localStorage` and sign in their place.
* **Files:** the deposit (or answer) carries the sealed manifest and `chunks`; chunks are uploaded afterwards, one per request, each once, and only while nobody has opened the deposit. An incomplete file does not open (`404`) and expires within 10 minutes: the last chunk restores the chosen lifetime, so nobody fills space with uploads never finished. Opening a `BurnAfterReading` file does not delete it but *claims* it: the relay picks a random token, keeps only its SHA-256 and returns it only to whoever opened; from then on the deposit does not reopen, each chunk goes only to whoever presents the token, at most once, and is deleted as it leaves; the deposit goes with the last chunk, and an abandoned download expires within an hour. An `UntilExpiry` file stays downloadable by anyone with the link until expiry. If an upload breaks off (network, `429`, `507`) the client keeps in memory id, sealed chunks and each index's state (`web/src/lib/files.ts`) and offers a retry that sends only the missing chunks: that is what saves an answer, which has already consumed the request. A `404` on an index whose earlier send may have arrived (network drop, `5xx`) means "already in", but only while an incomplete file can still live (10 minutes from the receipt, less for a shorter lifetime, minus a margin): after that, and on an index that surely did not arrive, it means the deposit is gone, and the sender is asked for a new request.
* **Chunks on R2, never in the vault's records:** the relay stores each chunk as an object in the R2 bucket `sigylo-chunks` (EU jurisdiction) under a random 128-bit name it picks (`IdSource::fresh_object`), which says nothing about the deposit. Before writing to R2, `Vault::reserve_chunk` refuses a chunk the deposit does not take (nothing is written) and records the name in the garbage for 15 minutes (`RESERVATION_SECONDS`); afterwards `Vault::put_chunk` turns the fresh reservation into a chunk, and a refused object is deleted at once. An index already taken is a refusal like the others (`404`). The vault keeps only name and size. Every chunk that leaves (burned, revoked, expired, with its deposit or alone) leaves name and size in the garbage, collected no sooner than 5 minutes (`GARBAGE_GRACE_SECONDS`); the cron deletes those objects from R2 and only then forgets them (`Vault::forget_garbage`), so an R2 error loses track of nothing. A chunk to burn is found (`Vault::open_chunk`), read from R2 and only then burned (`Vault::burn_chunk`), so an R2 error does not lose it; it disappears from R2 as it leaves. A revoked one disappears at once (`Vault::revoke` names its objects), an expired one within about 30 minutes (the cron runs every 15, and garbage waits 5 for the next run); a bucket lifecycle rule (8 days) is the backstop.
* **API (`worker/src/api.rs`):** `POST /api/secrets`, `POST /api/secrets/{id}/open`, `POST /api/secrets/{id}/revoke`, `POST /api/secrets/{id}/chunks/{n}`, `POST /api/secrets/{id}/chunks/{n}/open`, `POST /api/requests`, `GET /api/requests/{id}`, `POST /api/requests/{id}/answer`. Opening is always a POST: link previews and prefetches (GET) cannot burn a secret. Binary fields in unpadded base64url, except chunks, which travel as raw binary bodies (no 1 MiB base64 in the Worker's 10 ms of CPU). The body is validated (including the declared `Content-Length`, required on every route with a body: without it, `411` before reading) before it costs a Durable Object request.
* **Rate limits:** Cloudflare bindings `WRITE_LIMITER` (POST, 30/min) and `READ_LIMITER` (GET, 60/min) on every API call (GETs too: each costs a Durable Object request) per address, IPv6 per /64 (`limiter_key`); IPv6 POSTs also count per /48 (`NETWORK_WRITE_LIMITER`, 300/min, `network_key`), because a free tunnel gives anyone 65,536 /64s; kept in Cloudflare's memory, never stored by us.
* **Only from our pages:** a call with an `Origin` header other than the relay's origin gets `403` (`check_origin`), so another site's page cannot use its visitors' browsers to fill the custody around the per-address limit. Without `Origin` (the app shell) it passes.

## 3-bis. OPTIONAL ACCOUNTS (Access context, OPAQUE login)

* **What they are for:** a signed-in user finds in "Your seals" the secrets sealed while signed in and can destroy them from any device. Without an account everything works as before. No e-mail: only username and password.
* **OPAQUE (RFC 9807, `opaque-ke` 4.0):** the password never leaves the device, not even as a hash, and the server keeps only a record from which it cannot be tested offline. Suite: Ristretto255 OPRF, 3DH key exchange (Ristretto255, SHA-512), Argon2id v1.3 KSF 64 MiB, 3 passes, 1 lane (`HARDENING_*` in `suite.rs`). Passwords 8–1024 bytes; the name is lowercased (NFC in the client), 3–64 characters.
* **Relay keys:** all derived from a single Worker secret `OPAQUE_SERVER_SEED` (32 bytes base64url) with HKDF-SHA512: a deterministic `ServerSetup` (pinned by `tests/opaque_pin.rs`: if the seed or the derivation changes, every existing account stops working) and the HMAC key of `AccountId = HMAC-SHA256(k, "sigylo/v1/account\0" ‖ name)`. The accounts object never sees the name. The deploy workflow creates the secret if missing; it **must never be rotated** without an account migration.
* **Indistinguishability:** unknown name and wrong password give the same `401` (`opaque-ke` fake record); the one known limit is that registration reveals whether a name is taken (`409`).
* **Sessions:** 32-byte tokens; the server keeps only their HMAC-SHA256 under a key derived from `OPAQUE_SERVER_SEED` (`OpaqueKeys::session_digest`), so a copy of the store, or whoever could write to it, can hold a session record but never a matching token; 12-hour lifetime (`SESSION_SECONDS`, also enforced by `AccountLedger::open_session`); the client keeps it only in the tab's memory (a reload signs out). A session opens only for the account record the login verified: if the name changed hands between the record's read and the session (closed and registered again), the login gives `NotAuthentic`. At most 16 sessions per account (`MAX_SESSIONS`, enforced by `AccountLedger::open_session`): one more closes the one expiring first (the lowest digest on a tie, never the new one), before the ceiling is checked, so an account at its limit always signs in. "Sign out everywhere" (`close_sessions`) closes every session of the account, leaving account and keyring untouched. The state between the two login steps lives only in the accounts object's memory (`Scratch`) for 5 minutes and is single-use (`LOGIN_WINDOW_SECONDS`); a restart of the object drops it, and that login must start over.
* **Keyring:** `HKDF-SHA512(export_key, "sigylo/v1/keyring")` gives a 256-bit key that seals (a link-mode envelope, `Sealer::seal_with_link_key`) a JSON of seal ids and revocation tokens, never read links; at most 72 KiB and 300 seals. A write drops seals that expired before the session began by the relay's clock (`expires_at` minus 12 hours) or the device's, whichever is earlier, so a device clock running ahead never prunes live ones. Writes use an optimistic version: on `409 Conflict` the client rereads and reapplies the change. That version is not authenticated, so the sealed JSON also carries its own generation (`gen`, +1 per write; a keyring without it counts as 0) and each device remembers in `localStorage` the highest it has seen, under `sigylo.keyring.v1.` + 128 bits of SHA-256(`"sigylo/v1/keyring-watermark"` ‖ keyring key), never the name (`web/src/lib/keyring.ts`): an older copy (even "no keyring") gives `KeyringRolledBack`, a warning, and is never overwritten. Known limit: a device that has never seen the account has nothing to compare with, and storage that refuses turns the check off.
* **Throttle:** 10 attempts a minute per account and per budget, counted once for the whole world in the accounts object's memory (`VaultThrottle` → `Scratch::admit`: a one-minute window per key, never written to disk, swept on the way and by the cron; a restart resets it, which allows at most one more window, 10 attempts, per account and budget). Three separate budgets (`Budget`, keys from `throttle_bucket`; only the 32-byte key reaches the object, never the pass): the shared login, registering a free name, and each **device pass**. A taken name answers `409` before spending budget. Registrations and device logins have memory reserves of their own (§3-ter), so a flood of logins neither stops registrations nor fills the room of the owners' devices; `register/finish` files only a record that parses as an OPAQUE one (`OpaqueServer::check_record`, else `400`). After each login the relay hands out a pass (`HmacPasses`: 90-day expiry ‖ nonce ‖ HMAC over account and SHA-256 of the record, key from `OPAQUE_SERVER_SEED`, nothing stored); the client keeps it in `localStorage` (`sigylo.pass.v1`, under a hash of the name) and shows it at the next login, which spends a budget of its own: whoever guesses passwords on the name exhausts only the shared budget and does not lock out the owner's devices. A pass opens nothing, and a new record (the name passed to someone else) voids it. The `LOGIN_LIMITER` binding stays in front as a cheap first filter, but counts per Cloudflare location and is not enough alone. If either does not answer, the call is refused (fail closed).
* **No oracle in registration:** `register/start` for a taken name answers `409` at once without evaluating the OPRF: with the evaluation under the account's key, anyone holding the victim's KE2 could test passwords offline.
* **Sealed login state:** the `ServerLogin` state parked in the accounts object's memory is encrypted with XChaCha20-Poly1305 (key from `OPAQUE_SERVER_SEED`, AAD = account ‖ SHA-256 of the record): whoever could write a parked login can neither plant their own state nor move it to another account, and a login started before a name changed hands does not enter the new account.
* **API:** `POST /api/account/register/start|finish`, `POST /api/account/login/start|finish` (`login/start` accepts `pass`, `login/finish` returns it), `POST /api/account/logout`, `POST /api/account/logout/everywhere`, `GET|POST /api/account/keyring`, `POST /api/account/close`, with `Authorization: Bearer <token>` where a session is needed; `GET /api/account/canary` (public, see §6).
* **Known limits:** OPRF and 3DH are not post-quantum (transcripts travel inside TLS anyway; `opaque-ke` 4.1 will have a hybrid KEM); no password change or recovery: whoever forgets it loses the keyring, not the secrets.

## 3-ter. THE VAULT (Vault context, Durable Objects + R2)

* **Where custody lives:** a single Durable Object `SigyloVault`, created by name in the `eu` jurisdiction (`vault_adapters::DurableLink`), with its SQLite storage used only through the synchronous key-value API: no SQL, the format is ours (`crates/vault/src/core/records.rs`, `keys.rs`). Envelopes and chunks live in R2 (bucket `sigylo-chunks`) under random 128-bit names, never in the Durable Object, because its storage keeps 30 days of history (point-in-time recovery): a burned secret must not survive there. The Durable Object holds only ids, expiries, rules, revocation and claim digests, object names and sizes.
* **One step, one transaction:** every `Ledger` operation is a synchronous step inside `transactionSync` (`KeyValue::atomically`): all or nothing, and the Durable Object runs one step at a time, so burn-after-reading delivers at most once. `LedgerVault` interleaves the steps with R2: find, read from R2, then burn; reserve the envelope's name (in `garbage`, already counted in the cap), write to R2, then record, and delete the object if the ledger refuses. An R2 error or a Durable Object restart loses nothing: an envelope never recorded is collected by the cron.
* **Custody ceilings and daily thresholds:** lifetimes, incomplete files for 10 minutes, one-hour claim, chunk reservation (15 minutes) and garbage with 5 minutes' grace, as §3 says; a cap of 50 GiB of objects in R2 (envelopes, chunks and garbage together, `OBJECT_BYTES_CEILING`; past R2's free 10 GB a full store adds about $0.60 a month) and 1,000,000 records (`RECORD_CEILING`), kept in the usage record (`u`) and read without scans. A store at a ceiling first purges a batch of what has expired, then refuses with `507 StorageFull`; open, burn and revoke always work. The vault never holds a chunk's bytes; with the 30 POST a minute per address limit, a 10 MiB file costs 11 requests to upload and 11 to download. In addition, beyond 1,000,000 rows written in a (UTC) day nothing new is kept, while open, burn, revoke and purge go on, and beyond 2,000,000 purge and collection also wait for the next day (whatever expired is already invisible). The vault runs on the Workers Paid plan: past the 50 million included rows a month it costs $1 per million and nothing blocks, so the thresholds only cap the bill (about $1 a day for sealing). On the free plan (100,000 rows a day, then every write fails until UTC midnight) a flood would stop open, burn and revoke for everyone: the thresholds would have to go back under half that limit. Records are validated strictly (`decode`), and a damaged record gives `VaultUnavailable`, never a secret.
* **The wire:** the Worker talks to the vault with a single request per call (`RemoteVault` → binary `Call`/`Reply`, `serve` in the Durable Object). The claim token never crosses the wire, only its digest.
* **Accounts, a Durable Object of their own:** the Access store lives in a second class, `SigyloAccounts` (binding `ACCOUNTS`, migration `v2`), one instance named `accounts` in the `eu` jurisdiction (`DurableLink::named`), with its own storage, usage and daily counts: an account call can never reach custody's storage, nor the other way round. It answers only a POST to `/call` (`api::accounts_door`). The code is in the vault domain (`core/account_*.rs`, `application/{accounts,scratch,remote_accounts}.rs`): the Worker holds a `RemoteAccounts` (the `AccountStore` port, one Durable Object request per call: `register/start` 2, `register/finish` 1, `login/start` 3, `login/finish` 3, every session route 1, pinned by tests) and a `VaultThrottle`; the object runs `serve_accounts` over an `AccountLedger`. Calls and replies (`AccountCall`/`AccountReply`) have tags disjoint from custody's, so neither decodes as the other; no call lists, scans or ranges, each names the one key it must already know (pinned by a test). Every ledger method is a plain synchronous `fn`, one `transactionSync` step: the object runs one request at a time only up to its first `await`, and a ledger that never waits cannot see another request's half-done work.
* **Accounts on disk:** `a` + account id → the OPAQUE record (fixed size, so a known name's read does not vary with its keyring), `k` + account id → the sealed keyring and its version (missing = version 0), `s` + session digest → account and expiry, the indexes `m` (an account's sessions by expiry) and `e` (all sessions by expiry), and the usage record `w`; one ASCII letter, lowercase hex, fixed-width hex times (`core/account_keys.rs`), strict decoding and `format_pin` tests (`core/account_records.rs`). A record that does not decode gives `503 StoreUnavailable`, never another account's data; a delete driven by an index rereads the session first, and a stale index entry is just removed.
* **Accounts in memory (`Scratch`):** logins in progress (5 minutes) and attempt counters (1 minute) never touch disk, so a flood of guesses writes 0 rows and leaves nothing in the recovery history. Memory is counted in units (a counter 128, a parked login 384) in three pools: Shared, 16 MiB, for the shared login budget; a Registration reserve of 1 MiB and a Device reserve of 8 MiB, each overflowing into Shared once full. Guessing a name fills only Shared, so registrations and the owners' devices keep their room; a device's bucket holds one parked login at a time (a new one replaces it) and an account at most 16 live device buckets, so a stolen pass holds one slot, never the account's room. `admit` asks for the same room (512 units, 128 for a registration) whether the counter exists or not, so `429` versus `507` never tells whether someone else tried the name this minute; a full pool is a refusal (`429`), a full pool on parking `507`. At most about 40 MB of real memory. A restart (deploy, crash, eviction when idle) drops parked logins and counters: a retried login, and at most one more window of attempts. `Scratch`, `AccountLedger` and both objects' `serve` paths have no call that can panic (no `unwrap`, indexing or unchecked arithmetic), since the two classes may share an isolate; adversary tests feed garbage to both doors.
* **Account ceilings:** accounts do not expire, so they have ceilings of their own, answered `507 StorageFull`: 64 MiB for accounts and keyrings (512 per account plus its keyring's length, `ACCOUNT_BYTES_CEILING`) and 16 MiB for sessions (192 each, `SESSION_BYTES_CEILING`), kept in `w` without scans. `enroll` checks the name before the room, so a taken name stays `409` at the ceiling. At the ceiling you can still sign in (expired sessions are purged first, and an account at 16 sessions evicts before the check), read, and rewrite a keyring no larger than before; a stale keyring version answers `409 Conflict` before any ceiling.
* **Account daily thresholds, per class (UTC day, `core/account_limits.rs`):** 1,000,000 session rows (`SESSION_ROWS_PER_DAY`), 250,000 keyring rows (`KEYRING_ROWS_PER_DAY`, which overrides the "no larger keyring" promise above) and 10,000 new accounts (`ENROLLS_PER_DAY`, so filling the 64 MiB for good takes 13 days or more); past 2,000,000 rows in all the purge waits for the next day. Each stop answers `507` for its own class only, until midnight UTC: a flood of keyring writes or registrations cannot stop sign-in. Signing out, signing out everywhere and closing an account are never refused. Accounts are optional, so custody is unaffected.
* **The bill, both objects together:** the accounts object can write about 2 million rows a day in the worst case, on top of custody's 2 million: about 4 million a day, 120 million a month, about $70 a month above the 50 million included. Durable Object requests (3 per `login/start`) are capped only by the address limits. One object serves about 1,000 requests a second (Cloudflare's figure), so about 333 `login/start` a second; beyond that account calls, sign-out included, slow down or answer `503`, while custody, in its own object, goes on.
* **Recovery history (point-in-time recovery):** a Durable Object's storage keeps 30 days of history. For custody it holds only ids, expiries, digests and object names (the sealed bytes are in R2). For accounts it keeps `a`, `k`, `s`, `m` and `e` for 30 days after sign-out and closing: the account id (a keyed hash of the name), the OPAQUE record, the sealed keyring, and session expiry times, hence sign-in times (expiry minus 12 hours). **Never restore `SigyloAccounts`** from that history: it would bring back closed accounts and signed-out sessions still within their 12 hours.
* **Trust boundary:** with the database gone there is no relay role that may only execute functions. Whoever holds the Cloudflare deploy token or the Cloudflare account can deploy code that reads `OPAQUE_SERVER_SEED` and lists every `a` record, and then guess passwords offline, for accounts closed in the last 30 days too. The same holder could already serve an `index.html` that captures passwords (§5, known limit), so what this adds is past and closed accounts. The wire's lack of a listing call does not bind someone who deploys code. So the token stays in the `production` environment, scoped as §6 says, with 2FA on the Cloudflare account: token, account and environment are the single trust boundary for accounts.
* **Local only:** `VAULT_PLACEMENT = "local"` (passed by `scripts/e2e.sh` to `wrangler dev`, whose runtime has no jurisdictions) must never be in `wrangler.toml`, nor may anything of the database the relay no longer has (`DB_TLS`, `LEGACY_VAULT`, a `hyperdrive` table): the deploy fails if any is there, in any table or spelling (`scripts/local-switches.py` reads the TOML).

## 4. PERSISTENCE (Cloudflare only: Durable Objects, R2, memory)

| What | Where |
|---|---|
| Custody records: ids, expiries, rules, revocation and claim digests, object names and sizes | Durable Object `SigyloVault` (EU), SQLite storage through the key-value API |
| Sealed envelopes and file chunks | R2 bucket `sigylo-chunks` (EU), random 128-bit names |
| Accounts, sealed keyrings, sessions (keyed digests) | Durable Object `SigyloAccounts` (EU), same API |
| Logins in progress, attempt counters | `SigyloAccounts`' memory only |
| Per-address rate limits, `LOGIN_LIMITER` | Cloudflare's memory |

* No database, no other provider: nothing of PostgreSQL, Hyperdrive or Supabase is left in the code, and the deploy refuses their switches (§3-ter).
* The formats are ours: every record is decoded strictly, its layout pinned by `format_pin` tests (a change bumps its version byte); expiry is decided by the Worker's clock (`WorkerClock`) inside the Durable Object, and an expired record is invisible before it is purged. Every new kind of record that keeps bytes must be counted in its object's usage record (`u` for custody, `w` for accounts), which the ceilings read without scans.
* A cron every 15 minutes physically deletes what has expired: first in the vault (`purge_expired`; the objects of the chunks that go join the garbage), then it collects the due garbage and deletes the objects from R2, in batches of 1000, while it finds some and for at most 5 batches or 10 seconds; then it purges the accounts object (expired sessions on disk, logins and counters in memory).
* The Durable Object classes are born with the deploy (`[[migrations]]` in `wrangler.toml`: `v1` `SigyloVault`, `v2` `SigyloAccounts`, SQLite classes). Roll forward only: a rollback across a migration may be refused, and a version from before `v2` would look for the database that is gone.

## 5. WEB CLIENT AND CODE INTEGRITY

* Svelte 5 (runes) + strict TypeScript; no runtime dependency beyond the compiled code.
* Served by the Worker itself (Workers Static Assets): a single origin, hence `connect-src 'self'` and no CORS.
* **CSP** (`web/public/_headers`): `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, plus `Referrer-Policy: no-referrer`, COOP, CORP, HSTS, `nosniff`, `X-Frame-Options: DENY`. No `unsafe-inline`: no inline scripts or styles.
* **SRI** (`web/vite-plugin-integrity.ts`): sha384 `integrity` on scripts and stylesheets, and the `.wasm` is fetched with `fetch(url, { integrity })`.
* After opening, the key is removed from the address bar (`history.replaceState`).
* **UI:** everything follows the golden ratio φ (`web/src/lib/golden.ts`): Fibonacci spacing around 8 px, type in φ steps from 16 px, 610 px column, and a "sealing wax" OKLCH palette whose hues turn by the golden angle, light and dark themes. `app.css` fixes the values in hex; `web/tests/golden.test.ts` fails if they drift from the computation, if a colour or length outside the tokens appears, or if a pair loses WCAG contrast (text AAA 7:1, secondary text, errors and states AA 4.5:1, graphics 3:1).
* **Terms and privacy** (`web/src/lib/legal.ts`, pages `#/terms` and `#/privacy`, footer links in a new tab so an open secret link does not lose its fragment): text only, never `{@html}` (checked by tests). The Apache License 2.0 covers the code; the terms cover only the service on sigylo.net. Operator and contact live in `operator` and in the `NOTICE` file: a test fails CI, and so the deploy, while they contain `DA COMPILARE`. When a text changes, update `LEGAL_UPDATED`; when providers, kept data or maximum lifetime change, update the privacy notice. `web/public/.well-known/security.txt` (RFC 9116) and `SECURITY.md` say whom to report a vulnerability to: a test fails CI once the `Expires` date has passed.
* **Known limit:** whoever controls the hosting can serve a different `index.html`. SRI protects subresources, not the page itself. Whoever wants to avoid that has the app (below); signed and verifiable builds are deferred (§7).

**Installable app (`app/`, Tauri 2):**
* `vite build --mode app` (`npm run build:app`, into `web/dist-app`) produces the same page with the Wasm engine, embedded in the app: while the app runs no code comes from a server, and there is no updater.
* The page has no network: the app CSP (`vite-plugin-app.ts`, identical to the one in `tauri.conf.json`, checked by tests) has `connect-src 'self' ipc: http://ipc.localhost`. Relay calls go through the Rust command `relay` (`app/src/relay.rs`), which accepts only the API routes with their method (the account session token only on the routes that need it, validated and sent as `Authorization: Bearer`) and goes only to `https://sigylo.net/api`: no redirects, no cookies, HTTPS only, body ≤ 100 KiB, response ≤ 128 KiB. File chunks cross the IPC in canonical base64url (at most 1 MiB + 16 bytes, single-digit index) and travel to the relay as raw bytes. So the Worker stays without CORS.
* An opened file is saved to the Downloads folder: the webview follows only a `blob:` created by the page itself (always `application/octet-stream` with a download name), never shown. The page has only two permissions (`capabilities/main.json`: `allow-relay`, `allow-open-legal`), no Tauri or plugin permission, no `withGlobalTauri`, `freezePrototype` on; the webview does not navigate outside the bundle (`navigation.rs`).
* Links created in the app are `https://sigylo.net/#/…` (they open in any browser); a received link is pasted into the app's box (`linkFragment` accepts only `https://sigylo.net/` with a secret, revoke, request or inbox fragment). Terms and privacy open in the system browser.
* Release: `.github/workflows/app-release.yml` (an `app-v*` tag equal to the version in `tauri.conf.json`, or by hand from `main`) creates unsigned Linux, macOS and Windows installers in a draft release. Signing and stores need the owner's accounts. Mobile: crate ready (`mobile_entry_point`), native projects to be generated with `cargo tauri android init` / `ios init`.

## 6. DEPLOY

1. Cloudflare R2: `npx wrangler r2 bucket create sigylo-chunks --jurisdiction eu` and, as a backstop, `npx wrangler r2 bucket lifecycle add sigylo-chunks backstop --expire-days 8 --jurisdiction eu`, which the deploy workflow adds by itself if missing (the deploy token must be able to edit R2).
   Vault and accounts: the `SigyloVault` and `SigyloAccounts` Durable Objects are born with the deploy (`[[migrations]]` `v1` and `v2` in `wrangler.toml`, SQLite classes); the vault's R2 bucket is the same as the chunks'. Roll forward only (§4), and **never restore `SigyloAccounts`** from point-in-time recovery (§3-ter).
2. Publication on `https://sigylo.net` (Worker custom domain, `workers.dev` off). Normally done by `.github/workflows/deploy.yml`: it runs only on `main`, only after CI passed on that same commit (a run by hand asks the GitHub API for a green CI run of that commit, pushed to main), never from a pull request, and only if the commit is still the tip of `main`. Its secrets (`CLOUDFLARE_API_TOKEN`, "Edit Cloudflare Workers" template limited to this account and the sigylo.net zone, and `CLOUDFLARE_ACCOUNT_ID`) belong to the GitHub environment `production`, open to `main` only, never to the repository, so a workflow pushed on another branch cannot read them; token, environment and the Cloudflare account (with 2FA) are the single trust boundary for accounts (§3-ter). Every GitHub action is pinned to a commit (`uses: owner/action@<sha> # tag`, checked by CI): a moved tag of a third-party action would run next to the token and the page to publish. By hand: `(cd web && npm ci && npm run build)` then `(cd worker && npx wrangler deploy)`.
3. Worker secret `OPAQUE_SERVER_SEED` (§3-bis): after the deploy the workflow creates it with 32 random bytes if it does not exist and never touches it again. By hand: `openssl rand 32 | basenc --base64url | tr -d '=\n' | npx wrangler secret put OPAQUE_SERVER_SEED`. Without the secret accounts answer `503` and the rest works. **Canary:** `GET /api/account/canary` returns a public fingerprint of the secret (`OpaqueKeys::canary`, HKDF "canary"); the `OPAQUE_CANARY` variable in `worker/wrangler.toml` records the one the accounts were created with. When set, accounts answer `503` under any other secret, the workflow stops instead of creating a new secret when it is missing, and fails if the published canary differs; when empty, the workflow prints the value to paste.
4. In the sigylo.net zone turn off every Cloudflare feature that rewrites HTML (Rocket Loader, Email Obfuscation, automatic Web Analytics): they would break CSP and SRI. After every deploy the workflow checks that the served page is byte-for-byte identical to `web/dist/index.html` and carries the `_headers` CSP, and fails if the zone rewrites it.

## 7. DEFERRED (not in the MVP)

* **Non-exportable signing keys** in the verifiable client (Tauri, Secure Enclave / TPM); refusing an unexpected sender's answer already at the relay would need the relay to see who signs, so it stays client-side.
* **Accounts, second phase:** password change and recovery, OPAQUE with a hybrid post-quantum KEM (when `opaque-ke` 4.1 is stable), sessions that survive a reload. The link stays the capability: the account keeps only revocation tokens (§3-bis).
* **Accounts at rest:** encrypting account records and keyrings in `SigyloAccounts` under a key that can be shredded would shorten what the 30-day recovery history keeps; it would not help against the trust boundary (§3-ter), since that key would sit next to the seed. Expiring accounts that never stored a keyring, and a way to repair a store filled with spam other than wiping the `accounts` object, wait too: the daily cap on new accounts gives 13 days or more of warning.
* **Verifiable client:** signed, reproducible app builds, keys in Secure Enclave / TPM, or a signed browser extension. Opening `https://sigylo.net` links straight in the app (universal/app links) needs the developer accounts' identifiers.
* **Files over 10 MiB:** R2 storage is already there; it would need more chunks per file and, beyond some size, multipart upload.
* **Blind index:** not needed until server-side search exists.
